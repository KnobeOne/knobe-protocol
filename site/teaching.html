About
Instructor toolkit

A sealed record of coursework, from syllabus to submission.

Three browser tools on one engine: an instructor defines an assignment sequence once, each student seals their step against it, and a TA checks a whole batch at once. Every artifact is a plain-text .knobe.md file that records who made it, what it builds on, and the AI policy it was made under. Works with or without AI in the course, and rides Canvas features that already exist.

● Every tool on this page runs inside the browser page. Student work is never transmitted anywhere, to us or anyone else. That matters under FERPA: no third party processes the submissions.

The loop

A large course runs on a loop: the instructor designs, students submit, TAs grade, and disputes come back to the instructor. Each tool below serves one position in that loop. All three are tabs in Studio.

Instructor, once per assignment sequence

The Journey tab builds a sequence on a card-based form: each step names who seals it, what kind of work it is, what it builds on, and the AI policy it runs under. Sealing produces one journey file whose markdown body is a syllabus-ready description and whose payload carries the machine-readable steps. Instructor-authored steps (a reading, an assignment spec) can be sealed on the spot; their hashes flow back into the journey so student work can chain to them byte-exactly. Post the journey file to the Canvas assignment and paste the body into the description. No JSON appears at any point.

Student, per assignment

The student opens Studio's Create tab, loads the journey file from the assignment, and picks their step. The form fills itself: the right content type, the parent hashes, the course context, and the review status. The step's AI policy drives what the form asks for. A no-AI step asks for a sole-authorship declaration; a disclosure step adds a row for naming the AI and stating what it did and did not do. The student writes, seals, downloads one file, and uploads it to Canvas like any other file. The overhead is a form, not a workflow.

TA, per batch

Canvas's Download Submissions produces a zip. Unzip it and drag the folder into Studio's Cohort check tab, with the journey file loaded as the expectation. The result is one table: integrity verdict, declared author, AI disclosure, and whether each file chains to the assigned spec. Anomalies sort to the top; the clean majority needs no attention. The table exports as CSV for gradebook cross-reference. Grading itself stays in SpeedGrader.

End of term, and disputes

Drop one student's files into Cohort check and open the chain view: each file lists what it builds on and whether the hashes match. In a regrade or an academic-integrity dispute, both sides work from the same sealed record of what was submitted and what was declared, at the time it was sealed.

Canvas, step by step

The whole flow rides four Canvas features that already exist. Nothing installs, and no administrator is involved.

  1. Post the assignment. Attach the sealed journey file and paste the journey body into the assignment description.
  2. Set the submission type to File Uploads. One gotcha: if you restrict allowed file types, the list must include md, or Canvas will reject every submission. This is the single most common setup failure.
  3. Collect with Download Submissions on the assignment page. Canvas hands back one zip of every student's file.
  4. Grade in SpeedGrader as usual. A .knobe.md file is plain text; SpeedGrader displays it. The Cohort check table runs alongside, not instead.

Studio can also load a journey from a link (/studio/?journey=<url>) when the journey file is hosted openly, as the kit examples below are. Canvas attachments require a login, so a browser page cannot fetch them directly; for Canvas-hosted journeys, downloading and dragging the file in is the path that works, and it is the one the student handout teaches.

AI policy, in either direction

The toolkit takes no position on whether AI belongs in your course. It records the position you take. A step sealed under a prohibition carries the student's sole-authorship declaration. A step sealed under a disclosure policy carries a named AI contributor, marked non-rights-bearing, with the student's own account of what the AI did and what they did. The seal does not detect AI use, and nothing here is a detector. It replaces detection with declaration: a signed, hash-anchored statement the student makes at submission time, against the policy you set.

Accessibility adaptations

Alternate formats are part of the same loop. Studio's Adapt tab seals a plain-language version, translation, transcript, or description as its own file: bound to the exact source by hash, credited to the adapter and any reviewer, with an honest statement of what was preserved and what was omitted. Disability-services staff get provenance and credit that survive distribution; students get an alternate format that cannot be mistaken for the full text. The accessibility guide in the kit covers it in one page, and the design behind it is on the accessibility page.

For TAs who run an agent

The same checks run agentically. A TA with Claude Desktop or any MCP client can install knobe-mcp, point it at the unzipped submissions folder, and ask the agent to verify the batch and tabulate the declarations. The server runs locally and has no network code, so the FERPA posture is unchanged.

What this does not do

  • It does not detect AI writing, plagiarism, or contract cheating. It records declarations and verifies integrity; a false declaration remains a conduct matter, now with a signed record of exactly what was declared.
  • It does not enforce anything inside Canvas. A student can still upload a plain file with no seal; the Cohort check table shows that as an unreadable row, and your syllabus decides what that means.
  • It does not integrate with Canvas beyond files. An LTI 1.3 tool with one-click seal-and-submit would need a server and a Canvas administrator's install. The protocol supports building one; this site does not ship one.
  • If you reseal a journey mid-term, earlier submissions still chain to the spec hash that was actually assigned to them. That is the record working correctly, not drifting.
